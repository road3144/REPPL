1. 사용자가 접속
2. 쿠키가 없거나 만료된 경우에 새로 세션을 발급받음 -> 세션 기간은 한 1~2일????
3. 사용자가 이미지나 동영상을 드래그 하거나 파일을 추가하여 업로드함(여러개 업로드 가능)
4. 그러면 브라우저에서 서버에 S3로 올릴 presigned url을 발급해줌(각각의 파일별로) 또한 서버에서는 현재 세션에 대해 사용자가 올린 파일들에 대해 key값들을 저장함
    
    지금까지 redis에 저장된 것
    세션 목록 : {사용자1}
    사용자1 -> {key1, key2, key3.....}
    
5. 사용자가 브라우저에 올린 파일을 삭제할 수도 있음 -> 이 것은 그냥 브라우저단에서 캐싱된 파일 삭제하는 형식만. 서버와 작용x
6. 사용자가 이제 원하는 파일들(동영상1, 사진 여러장)의 작업을 원한다면 이 파일들의 키값을 서버에 전송 -> 파일 형식들은 브라우저단, 서버단에서 이중체크하면 좋을듯함
7. 서버는 이 키값들을 받아서 현제 세션에 대해 저장되어있는 키값들을 보고, 해당이 안되는 키값이 있으면 S3로 삭제 요청을 보냄
8. 그리고 해당되는 키값들과 해당 영상의 구역 등을 모아서 하나의 Job을 생성함. 이 Job은 Redis에 저장됨
9. 또한 해당 세션에 해당하는 세션->파일목록 데이터는 flush
    
    지금까지 redis에 저장된 것
    세션 목록 : {사용자1}
    사용자 1 -> {Job1}
    {Job1[key,key,time...]}
    
10. Spring이 Job을 Redis에 저장하며 이 Job을 동시에 queue에 저장함.
11. GPU 서버가 queue에 쌓인 작업을 받아서 처리함
12. GPU 서버가 작업을 처리하며 진행률을 queue에 넣음
13. Spring 서버는 이 queue를 받아서 해당하는 Job의 세션에 Socket 통신으로 실시간 반영
14. 작업이 완료되면 queue에 작업 완료를 저장 -> Spring은 이를 받아서 presigned url을 발급(이건 HTTP통신)
15. GPU서버가 영상 업로드 후 완료를 보냄 -> 이건 queue로
16. 서버가 Socket통신으로 다운로드 가능 반영
17. 사용자가 다운로드 url 요청 -> public한 url 발급(여기서 세션이 그 Job을 가지고 있는가를 체크해주면 좋을듯)
